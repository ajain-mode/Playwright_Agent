What We Built — The Agent Pipeline

Outcome: Written test cases (CSV, Excel, or plain text) flow through a four-agent pipeline and emerge as validated, runnable Playwright test scripts — with AI filling gaps where rules alone cannot, and automated checks ensuring nothing is silently dropped. Delivered: 24 billing toggle and 4 DFB test scripts successfully generated through this architecture.

The pipeline combines deterministic automation rules (proven patterns, real UI locators from application source code) with Claude AI calls at four strategic points. Every AI-generated script is reviewed by the Quality Guardian and Coverage Ensurer before it is saved.

✦ AI Script Writer
Claude · 4 generation calls

Writes and adapts test scripts from natural-language test cases. Uses Claude CLI as the primary engine; Anthropic API as backup.

① Step Interpreter
Agent 1 · StepProcessor

Reads each test step and understands intent — which screen, which tab, edit vs view mode, which application (BTMS/DME/TNX).

② Code Mapper
Agent 2 · POMMethodMatcher

Maps understood steps to proven automation actions using 130+ patterns and 5,900+ real UI element IDs from application source.

③ Quality Guardian
Agent 3 · SpecValidator

Validates every generated script — auto-fixes violations, checks step coverage, enforces quality rules. Up to 2 correction passes.

④ Coverage Ensurer
Agent 4 · SpecFeedbackLoop  ·  1 pass · up to 8 missing steps filled

Compares the finished script against the original test case. Injects code for steps that were missed; flags uncertain matches for human review; triggers a final Quality Guardian pass if changes were made.

End-to-End Pipeline — How a Test Case Becomes a Script

✦ AI Script Writer — Four Claude Calls in the Pipeline

Claude is invoked at four strategic points. Each call uses governed prompts (framework schema, quality rules, reference test patterns). If a call cannot produce a result, the pipeline falls back to the next tier automatically.

CallBusiness NameWhat It DoesWhen It RunsIf It Fails
Call 1 Data Enricher Fills in missing test data fields (customer name, rates, office code, etc.) that could not be parsed from the written test case Before script generation, when test data is incomplete Continues with partial data; warning logged
Call 2 Full Script Writer Writes the entire test script in one pass, using a proven reference test as a structural template First attempt for every test case (when ≤ 40 steps and a reference exists) Falls back to Call 3 or rule-based generation
Call 3 Smart Adapter Clones a proven reference test and rewrites only the steps that differ from the new test case When the new test case is ≥ 70% similar to an existing automated test Keeps reference code or falls back to Call 4
Call 4 Step Writer Writes automation code for individual steps that no rule or pattern could match Last resort — when Step Interpreter + Code Mapper cannot resolve a step Placeholder flagged for manual completion

AI engine: Claude Sonnet 4.6 via Claude CLI (primary) → Anthropic API (secondary fallback if CLI unavailable). Generation order: Call 2 → Call 3 → Rule-based (Step Interpreter + Code Mapper) → Call 4. Safety net: All AI output passes through Quality Guardian and Coverage Ensurer before saving.

Upstream Gaps & Next Steps

The pipeline is built and working — but its effectiveness depends on the quality of inputs. Thin test cases, undocumented business rules, or restricted application access will limit what the agents and AI Script Writer can produce.

① Test Cases Lack Sufficient Detail

  • Testmo cases must include full step-by-step actions and expected outcomes — the agents cannot work from high-level summaries
  • Manual QA spends 3–5 hours per test case reaching that level of detail — the largest upstream effort today
  • Without sufficient detail, automated spec generation is inaccurate and requires heavy manual correction

② Tribal Knowledge — Scenarios Without Executable Steps

  • Test scenarios and business context exist in JIRA and team knowledge — the what is often documented
  • Detailed step-by-step instructions the agent pipeline can use are frequently missing — the how is not
  • Without agent-ready steps, precondition paths and business rules cannot be automated reliably

③ Limited Application Source Access

The UI Element Index currently syncs BTMS and DME repos only. Other products under test may lack ingested context for locator discovery.

  • Without source access, the Code Mapper cannot discover new UI element IDs
  • Broader repo sync permissions needed for full product coverage

④ Execution Time — Monolithic Scripts

Large test cases become single long-running scripts rather than phased, reusable segments — increasing run time and debug effort.

  • No decomposition into shared preconditions or phased build-up
  • Multi-app flows (BTMS → DME → TNX) multiply wall-clock time per run
  • Example: DFB-89214 — 768 lines, 103 steps, three applications

Recommended Next Steps

  • Enrich test cases with explicit expected results per step
  • Add agent-ready step detail to JIRA scenarios
  • Approve additional application repo sync for products under test
  • Decompose large cases into phased specs or shared fixtures
  • Grow the reference test catalog per category
  • Cap step count per generated script with continuation links
