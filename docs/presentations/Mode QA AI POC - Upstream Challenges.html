Upstream Challenges & What To Do

The QA AI Agent pipeline is built and delivering scripts — but output quality and scale depend on inputs, access, and how large cases are structured.

Key message: The agent cannot invent executable steps from thin scenarios. Investment upstream — detailed test cases, documented preconditions, broader app source access, and sensible script sizing — directly reduces manual rework after generation.
1
Highest impact today

Test Cases Lack Sufficient Detail

Challenge

  • Testmo cases often lack full step-by-step actions and explicit expected results per step
  • Manual QA spends 3–5 hours per test case reaching agent-ready detail — the largest upstream effort
  • High-level summaries produce inaccurate scripts and heavy post-generation correction

What to do

  • Adopt a Testmo template: numbered steps, action, and expected result for every step
  • Block generation until cases pass a minimum detail checklist (no orphan steps, no vague expecteds)
  • Maintain canonical step prose in sample-testcases.csv as the traceability source
  • Budget 3–5 hours per case for enrichment before first agent run — not after failed generation
2
Process & knowledge

Tribal Knowledge — Scenarios Without Executable Steps

Challenge

  • JIRA and team knowledge document the what — business intent and scenario title
  • The how — navigation path, data values, precondition order — is often missing
  • Office setup, user switch, multi-app hops, and billing rules cannot be automated without executable steps

What to do

  • Add agent-ready step detail to JIRA scenarios before they enter the Testmo / generation queue
  • Document standard precondition bands (office, agent, customer, load) as reusable step blocks in the testcase catalog
  • Pair domain experts with QA during enrichment — capture tribal knowledge as numbered steps, not chat notes
  • Use proven reference specs (e.g. billing toggle, DFB) as templates when a new case is similar
3
Platform access

Limited Application Source Access

Challenge

  • UI Element Index currently syncs BTMS and DME repos only (5,900+ elements indexed)
  • Other products under test may lack ingested HTML context for locator discovery
  • Without source access, Code Mapper cannot discover new element IDs — locators must not be guessed

What to do

  • Approve additional application repo sync for every product targeted by AI-generated automation
  • Refresh app source cache when UI releases ship — index invalidates on repo update automatically
  • For gaps, flag POM methods for manual locator lookup rather than accepting guessed XPath in specs
  • Extend AppSourceIndexer scan paths as new apps join the test scope (TNX, etc.)
4
Execution & maintainability

Monolithic Scripts — Long Run Time & Debug Cost

Challenge

  • Large test cases become single long-running scripts instead of phased, reusable segments
  • Multi-app flows (BTMS → DME → TNX) multiply wall-clock time per run
  • Example: DFB-89214 — 768 lines, 103 steps, three applications in one spec

What to do

  • Decompose large cases into phased specs or shared fixtures (office preconditions vs. scenario body)
  • Cap step count per generated script; link continuations across related specs where the testcase allows
  • Grow the reference test catalog per category so similar cases clone instead of generating monoliths
  • Prefer shared helpers (setupOfficePreConditions, etc.) only where the written case permits bundling
